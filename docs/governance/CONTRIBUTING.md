# Editorial governance for model changes

The frozen pilot and its authored interpretations are a versioned operational baseline, not a psychometrically validated ontology. [Model release 1.0.0](../../data/releases/model-release-v1.json) records the exact existing bank, registry, source, review, rule, route, affinity, scale, and runtime content. It records earlier review artifacts; it does **not** invent a new human approval. New files in the candidate bank or a proposal folder do not activate new production inference.

## Scope and lifecycle

| Object | Draft/review location | Production inclusion | Historical rule |
| --- | --- | --- | --- |
| Item and response options | Candidate bank and content review | Exact revision in an explicit route and release | Keep old bank/revision and scale snapshot |
| Construct, proposition, direct or derived rule | Registry/model proposal | `publicRuleIds` or derived rule in a new model release | Keep old model and result semantics |
| Research-only classification | Model proposal | Explicit research-only list; never a public result | Keep old classification snapshot |
| Tradition and criterion | Affinity catalog proposal | New independently versioned catalog | Keep old doctrine and mapping snapshot |
| Source | Registry/ledger and claim links | Referenced by an approved production object | Keep old citation record and source snapshot |
| Route and result semantics | Route/model proposal | New route/semantics release | Keep old selection/evidence behavior |

Useful states are `draft → under_review → approved → released`, plus `rejected` or `withdrawn` for proposals. Existing item `candidate` and construct `provisional` labels retain their original meanings; a reviewed frozen pilot item is eligible through its content-review decision and exact route inclusion, not by relabeling every bank item `production`. `deprecated`, `research-only`, `blocked`, and `unresolved` have object-specific meanings and must never be collapsed into one status field.

## Change classes and version consequences

| Class | Typical example | Minimum consequence |
| --- | --- | --- |
| `editorial_only` | Documentation typo or metadata that cannot affect interpretation | No structured proposal; if a pinned production artifact changes, use a new artifact/release and document the editorial change in release notes and normal code review |
| `semantic_clarification` | Meaning-preserving item rewording | Proposal, philosophical review, new displayed wording revision/version, regression review |
| `substantive_revision` | Different proposition, answer meaning, evidence threshold, or rule | Proposal, source-linked rationale, new component version and file, behavioral fixtures |
| `new_object` | New construct, item, rule, tradition | Proposal and explicit inclusion in a release; creation alone is inert |
| `deprecation` | Stop assigning an item or showing a rule | New route/model/catalog version; old object remains resolvable |
| `split` / `merge` | Separate or combine concepts | New IDs where meaning changes, old IDs retained, no inferred transfer of historical answers |
| `reclassification` | Direct → derived, research-only → public, or public → research-only | New model version and tests for results and affinity; a promotion to public use also needs the exact reviewed proposition and a matching rule-linked supporting source claim |
| `source_correction` | Replace a citation supporting doctrine | New source snapshot, dependent-claim review, new affected component version |

Punctuation in an unreleased draft may be corrected without an item revision. Once wording has been shown to respondents, exact historical wording must remain reconstructible: even a nonsemantic display correction needs a new wording artifact or revision. Changing “usually” to “always”, altering option meanings, or moving evidence between support and opposition is meaning-sensitive regardless of the contributor's intent. A new affinity defining commitment requires a new catalog file/version. A new route item set requires a new route file/version. Component versions evolve independently; the model release manifest binds the complete tuple.

## Propose, inspect, test, release

1. Search the registry, model, research-only entries, and affinity catalog for synonyms and neighbors before creating another object. A new political policy item must explain its underlying proposition, why a general item is insufficient, and jurisdiction limits.
2. Copy [the JSON proposal template](templates/model-change.json) into `data/governance/proposals/MCP-YYYY-NNN.json`; use the relevant short [type prompts](templates/item-revision.md). The [schema](../../schemas/model-change-proposal.schema.json) and runtime validator check structure. Substantive proposals specify exact proposition, neighbors, non-entailments, sources linked to individual claims, scholarly disagreement, alternatives, respondent impact, tests, and migration.
3. Run `node scripts/model-governance.mjs impact --type proposition --id RULE_ID` (or `item`, `construct`, `source`, `tradition`) before editing. Review all affected routes, comparisons, coverage records, result domains, affinities, wording, and source trails. A route edge means it assigns at least one exact evidence item revision, not that the rule's threshold is reachable or its inference valid; use the route-opportunity report for that separate check. Run `node scripts/model-governance.mjs report` for provenance gaps.
4. Add a new versioned file rather than editing a released artifact in place. Keep the old file and references. Add positive, negative, mixed, missing, contradictory where relevant, false-positive-neighbor, and historical fixtures for inference changes. A citation is not a behavioral test.
5. Record the needed review roles. Meaning-sensitive philosophical changes need philosophical and engineering review; route changes need both. Measurement claims need actual response data; privacy-changing research exports need privacy review. AI review may fulfill these roles when it records its evidence and limitations; no human sign-off is a release prerequisite. One reviewer may fulfill multiple roles, with each review recorded separately.
6. Compare the proposed release with the current baseline using `node scripts/model-governance.mjs diff --from data/releases/model-release-v1.1.0.json --to current`. The `notes` subcommand groups user-visible, editorial, model/research, and deprecation changes. The diff is conservative: it flags changed fields as meaning-sensitive unless explicitly narrow editorial metadata is known.
   For a synthetic completed administration that both releases can interpret, `node scripts/preview-model-impact.mjs --from data/releases/model-release-v1.1.0.json --to current --session /path/to/synthetic-session.json` shows proposition, derived, and affinity state changes. It reports incompatibility rather than inventing a cross-version comparison when exact item revisions or routes differ. It is a software regression tool, never empirical validation.
7. After proposals are approved, run the successor release workflow:
   - For an orchestrated release plan: `node scripts/release-successor.mjs --plan data/releases/plans/model-release-X.Y.Z.json`. This chains builder execution, release manifest capture, active pilot evidence disposition audit (`audit-pilot-evidence.mjs --active --write`), academic/sync pointer derivation, and governance verification deterministically.
   - To verify reproducibility from clean base before merging: `node scripts/release-successor.mjs --plan data/releases/plans/model-release-X.Y.Z.json --verify --base origin/main`.
   - Alternatively, run individual stages: `node scripts/build-model-release.mjs --new-version model-release-X.Y.Z --out data/releases/model-release-vX.Y.Z.json`, then `node scripts/audit-pilot-evidence.mjs --active --write`, then `npm run build:academic`.
   Commit new artifacts, proposal records, release notes, and manifest together. `npm test` and `node scripts/model-governance.mjs verify` must pass. All successor releases must reproduce identically from clean checkout without manual pointer fixups.

For a model release after `1.1.0` that changes an archived module, first run `npm run model:archive-engine -- --version engine-source-X.Y.Z`. The command copies the inference, route, and affinity modules into a new immutable archive with per-file hashes. Set `data/current.json` `engineSource` to its version and manifest path, then use the normal model release command. The release requires an approved proposal affecting `result_semantics:engine-source` with `engine_source` in `release.components`. Startup compares live modules with the pinned source hashes. Historical release `1.0.0` predates this mechanism and cannot acquire a retrospective code pin.

## Sources and disagreement

Use source types according to the claim: primary text and specialist scholarship for doctrine or historical attribution; peer-reviewed or scale-development work for measurement claims; SEP/IEP and academic books for careful secondary synthesis. There is no universal source score. `sourceClaims` states what each source actually supports, challenges, or contextualizes. For a new or meaning-sensitive proposition, derived rule, tradition, or criterion, a reviewed `supports` claim is required; context citations alone do not authorize inference. The exact reviewed claim must be retained in that object's `sourceClaims` in the new versioned artifact, and its source ID must be in the object's declared `sourceIds` (or the tradition's primary/secondary source IDs). The release gate checks this link. It records the scholarly basis for the distinction, not empirical validation of the item, evidence threshold, or affinity. The dependency report traces `source → claim/construct → rule → affinity`, while a result row already exposes its rule and sources. A bibliography attached only to a domain cannot authorize a new inference. Serious alternative readings belong in the proposal and, when they affect users, in the doctrine or result boundary. Do not create multiple production constructs for minor scholarly disagreements.

For every new or meaning-sensitive public proposition or derived rule, also store the exact proposal `philosophicalBasis.proposition` as the rule's `proposition` in its versioned model artifact. The release gate requires equality. A broad `scope` string cannot stand in for this reviewed inference target. Research-only → public membership changes are reported per rule in the semantic diff and require a reclassification proposal with the same exact proposition and supporting claim, even when the rule's other bytes are unchanged. Demotions also require a reviewed reclassification or deprecation proposal. These requirements do not rewrite the frozen pilot.

`node scripts/model-governance.mjs trace --type proposition --id RULE_ID` shows each mapped item's exact revision, authored support and opposition values, and duplicate-control unit. A derived-rule trace shows each prerequisite state; a tradition trace shows criterion doctrine, role, mapping status, and expected proposition state. `directSourceLinks` distinguishes sources cited by the target object from `upstreamSourceIds` encountered through an item, construct, or dependency. Source edges carry reviewed rule-linked claim text and its `supports`/`challenges`/`context` relationship when available. An older source-record claim is marked `source_record_claim`; citation-only edges are marked `topic_only`. Respondent result details make the same distinction: rule-linked claims are shown with their relationship, while a source-record claim is explicitly labeled as broader context. The graph and UI report provenance metadata; neither verifies that a question validly measures the proposition.

The current provenance report still flags several legacy source classifications, including project-authored `project-theory`. These are review targets, not automatic deletions or newly validated evidence. The baseline has extensive regression suites but no complete per-rule fixture index; a new rule proposal must name its own fixtures. A material item wording change requires a new item revision and corresponding route/result review.

The report also exposes `claimLevelProvenance` for public interpretation rules. It distinguishes claim text retained on the rule, generic claim text in a source record, and links with neither. In active release 1.5.0, 110 of 209 rule-to-source references lack an explicit `claim` or `implication` field in the model's source record; 49 public rules have no such text on any cited source, and 32 have a mix. These numbers describe **metadata traceability**, not a judgment that the scholarship is irrelevant or that the rule is false. Many older records have only a broad `use` topic. Reviewers must inspect the exact proposition and answer meanings against the source before adding claim text in a newly versioned source/model release. The result UI identifies these topic-level citations rather than silently presenting them as claim-level support.

The report separately counts `ruleLinkedSupportingClaimReferences` and lists `rulesWithoutRuleLinkedSupportingClaim`. A rule-linked `challenges` or `context` claim cannot count as supporting academic basis. The active model has eight rule-linked supporting claims among its 144 public rules, including the scoped OM14 method, protected federal division, moral truth-claim semantics, and Quick public testability. This is a review queue, not proof that each cited source is irrelevant. [EP10 revelation](REVELATION_JUSTIFICATION_REVIEW.md) is a draft example of checking the source's actual claim against the exact item meanings before any new version is approved.

The same report exposes `explicitPropositionCoverage`: 21 of 144 active public rules store an explicit `proposition`; 123 retain only a legacy `scope` label. The list is an editorial review queue, not a claim that all 125 rules are invalid. Respondent details identify scope-derived wording, and any future revision of those rules must record the exact reviewed proposition. The historical 1.1.0 model retains 15 of 141.

`affinityLegacyScopeDependencies` names every catalog criterion whose mapped direct or partial rule has only a legacy scope label. It also lists every mapping whose rule lacks a valid rule-linked supporting source claim, including mappings to explicit propositions. The original six-entry catalog had 16 scope-only criteria and 18 source-unlinked criteria among 19 direct or partial mappings. Use the live report for the active eleven-entry catalog. Review each exact doctrine, rule scope, answer meanings, neighboring views, criterion and rule sources, and false positives before a new affinity release changes the mapping. The report is a dependency inventory, not a blanket judgment that the current mapping is true or false.

`routeEvidenceOpportunities` in the same report compares Quick, Standard, and Full against each public rule's exact mapped item revisions and authored evidence units. For every direct or partial affinity criterion it lists administered and omitted mapped items, available support and opposition units, the rule's minimum, and whether the route can reach that minimum in both directions (`thresholdReachable`). It also lists public rules that sit exactly at the minimum in both directions. In the current Full route, `construct-NE15` reaches its two-unit minimum with `NEI100@1` and `NEI101@1` while mapped `NEI102@1` is omitted. These are **opportunities for authored inference**, not observed respondent evidence, independent psychometric indicators, or proof that a criterion is doctrinally measured. Inspect item meaning and neighboring views before changing a rule or affinity mapping.

The release gate rejects a new or changed direct/partial affinity criterion if its mapped public rule lacks either an explicit `proposition` or a rule-linked supporting source claim. A new derived mapping needs an exact derived conclusion, a rule-linked supporting source claim, and exact public prerequisites with their own linked supporting claims; the catalog validator enforces the same derived dependency boundary at runtime. Approve versioned rule revisions with the reviewed propositions and claims in the same release, map to different reviewed propositions, or leave the doctrine unmeasured. A source citation or legacy scope label alone cannot authorize a new doctrinal inference. These release guards apply to newly added traditions too; the frozen catalog remains available as historical content and its unresolved direct mappings are qualified in respondent-facing presentation.

For a changed criterion, the released `doctrine` text must also equal the proposal's exact `philosophicalBasis.proposition`. Reviewers should write that field as the criterion's doctrinal claim. A neighboring-view rationale belongs in the proposal's other fields; it cannot silently replace the approved doctrine in the catalog.

## Historical behavior

Deprecate by excluding an object from **new** routes, rules, or catalog publication while retaining its old definition and versioned artifact. Record a successor link when one exists. A split preserves the old object and adds new IDs with an explicit relationship; a merge never assumes an answer to either predecessor supports the merged proposition. No governance operation rewrites raw responses. A current reinterpretation of old answers must be separately labeled from the original result. The release verifier checks the exact current tuple; archived manifests and artifacts must remain available for historical replay and rollback.
